Vhite is currently a solid early CLI linting and safe-fix tool for JavaScript frontends. It already has:

- Recursive frontend file discovery
- JavaScript, JSX, HTML, and CSS scanning
- AST parsing with Espree
- Rules for TODOs, `debugger`, console logs, empty blocks, empty catches, unused imports, and hardcoded secrets
- Rule disabling through `vhite.config.json`
- Interactive fix approval
- Backups and rollback when a fix does not remove the finding
- Markdown run reports
- Tests and CLI automation support

The biggest opportunity is to make it useful every day, faster on real projects, and more trustworthy than a basic lint script.

## Highest-value features to add first

1. **Command options**

Support commands such as:

```text
vhite scan
vhite fix
vhite init
vhite rules
vhite explain <rule>
vhite report
vhite restore
vhite version
```

Add flags such as:

```text
--fix
--check
--format text
--format json
--format markdown
--quiet
--verbose
--no-color
--rule rule-name
--disable rule-name
--include path
--exclude path
--stdin
--watch
```

2. **Proper exit codes**

CI tools need predictable behavior:

- `0`: no issues
- `1`: issues found
- `2`: invalid configuration or runtime failure
- `3`: fixes were applied
- `4`: fixes were rolled back

Allow `--fix` to return success only if the final scan is clean.

3. **JSON and SARIF output**

Add machine-readable reports for:

- GitHub Code Scanning
- GitLab
- VS Code integrations
- CI dashboards
- Custom scripts

Each issue should include:

```json
{
  "rule": "no-console-log",
  "file": "src/App.jsx",
  "line": 14,
  "column": 5,
  "severity": "warning",
  "message": "..."
}
```

4. **Columns and ranges**

Many findings currently only report a line. Add:

- Start column
- End column
- Start offset
- End offset
- A code snippet
- A suggested replacement

This makes editor integrations and precise fixes possible.

5. **Severity levels**

Give every rule a severity:

- `error`
- `warning`
- `info`

Allow configuration like:

```json
{
  "rules": {
    "no-console-log": "error",
    "leftover-todo": "warning",
    "hardcoded-secret": "error"
  }
}
```

6. **Rule configuration**

Rules should accept options, for example:

```json
{
  "rules": {
    "no-console-log": {
      "severity": "warning",
      "allow": ["error", "warn"]
    },
    "no-todo": {
      "severity": "info",
      "allow": ["TODO: remove later"]
    }
  }
}
```

7. **Baseline support**

Large existing projects need a gradual adoption mode:

```text
vhite baseline create
vhite --baseline .vhite-baseline.json
```

Existing findings are ignored, while new findings fail CI.

8. **Inline suppression comments**

Support controlled exceptions:

```js
// vhite-disable-next-line no-console-log
console.log("Allowed for local debugging");
```

Also support:

```js
// vhite-disable no-console-log
// vhite-enable no-console-log
```

Require a reason optionally:

```js
// vhite-disable-next-line no-console-log -- reason: temporary migration log
```

9. **Watch mode**

Watch files and rescan after every save:

```text
vhite --watch
```

Show only changed findings and clear resolved issues.

10. **Git-aware scanning**

Add options to scan:

- Only changed files
- Files changed from `main`
- Staged files
- Files in the current commit

Examples:

```text
vhite --changed
vhite --staged
vhite --since HEAD~1
```

This would make Vhite much faster in pre-commit workflows.

- Autoplaying media
- Missing captions

- Duplicate IDs
